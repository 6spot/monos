### Accepted correction variant

The strongest economical loop uses the same Task/Node/PR for both result versions:

1. Establish a **genuine provider wait** before first Accept, for example a supported
   classic required check on the candidate that is still pending. Record the
   fixture-produced context as provider-readiness evidence, never as native test
   evidence. Confirm the literal policy/head and that no merge effect was admitted.
   Accept can freeze an eligible prepared result before merge readiness; do not
   stop the worker or insert a database hold to manufacture this state.
2. Execute actual prepare/confirm/Accept against result A. Retain exact proposal,
   content digest, confirmation, batch, cutoff and original Owner envelopes.
   Append one ordinary later question. If answered before correction, retain the
   actual reply; if not, retain its actual pending state. Its status is not forced.
3. Request Changes with exact current review basis and accepted-batch version,
   asking a concrete within-scope improvement that the existing Node can handle.
   Keep the required provider wait while confirming atomic revocation and no PUT.
   The public PR stays open and its identity/branch remain fixed.
4. Observe genuine scratch `reconsider_input` first, then `route_feedback`, each
   using its actual shared Planner owner and bundled CLI. A no-work answer records
   `resolve_review_input`, without a second chat reply or input reset. Main routing
   performs actual `apply_review_rework`; do not provide an outcome driver.
5. Observe the same Node at the next activation, unchanged Task/Spec/Plan and
   existing integrated private work. Native work produces result B; independently
   check the requested improvement and the unchanged original behavior/files.
   Automatic publication advances the same branch/PR without force or recreation.
6. Obtain a fresh exact result-B proposal/confirmation/Accept; old approval remains
   revoked and cannot carry. Settle only the marked supported check through its
   real producer after validating result B independently. Observe actual App
   issuance, head-bound readiness and one expected-head merge. Retain actual final
   Git/provider identity and tree, completed Task and all original histories.

**Ordering matters:** `main.ts` pumps every second. First Accept followed by a
manual correction is not a safe race strategy; a ready result can merge before
correction. Unknown/started/finalized merge must refuse correction. If an authorized
genuine wait is unavailable, unaccepted Request Changes can still prove installed
scratch review and same-lineage coding, but it does **not** prove installed accepted
revocation or late-input restoration. Resolve that scope before admission rather
than relabel the weaker flow afterward.

  Preserve command/log/native identity and use actual exact Owner Stop/Retry after
  settlement. No SQL status repair, implementation injection, model substitution
  or invented success checkpoint. A bounded observer deadline is not a product
  silence timeout.
- Review issue requires its actual Owner answer and same unresolved operation with
  incremented version/new source after original settlement. Withdrawal/Cancel
  fences immediately but does not imply capacity/effects already stopped. Do not
  fabricate Issue/Dismiss paths to expand this happy-path installed trial; reuse
  their accepted PG/browser evidence unless the native flow genuinely reaches one.
- Uncertain original push/PR/merge keeps its own intent/result/claim and reconciles
  read-only. Missing ACK/absence cannot justify a new identity. A completed/unknown
  merge forbids Request Changes; do not close/reopen/reset/revert to force the plan.
- Installation failure preserves intent/backup and old/new binary identities.
  Root restores only a demonstrably compatible component set after physical idle
  proof. Database history is never restored over new receipts; migration commit
  changes the available rollback image boundary.
- Failed synthetic work is ended through its actual Owner controls and exact owned
  cleanup capability. Preserve its public branch, PR truth, private work and
  journals. Never alter old accepted Tasks or unrelated services to obtain idle.
- Once current installed boundaries, final scoped ownership/history and independent
  review pass, stop effects/testing and hand off integration evidence. This research
  authorizes no host action and makes no installed-success claim.
