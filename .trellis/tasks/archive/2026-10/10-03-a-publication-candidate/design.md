# Controlled local publication candidate

## Source and decisions

Read [architecture](../../../ARCHITECTURE.md), modules 04/05/06/07/08/09 and the current layer specs. The accepted upstream source is `ac2b142`, archive `0803282`, journal session 27. Source-backed research: [Runner](research/runner-candidate-design.md), [backend](research/backend-candidate-design.md), [policy](research/policy-and-upstream-baseline.md). These are proposals; this document resolves their policy differences.

This leaf implements local construction, scans, exact local commands and Owner inspection. Remote push/PR/check/merge, final delivery acceptance and correction workflow remain the subsequent leaves. Standing development authorization does not manufacture a product Owner finding override.

## Owning boundary

The missing behavior is durable local preparation from an already completed, retained Git result. It belongs to Delivery system operations and Runner service-private Git storage. Neither a released Runtime Attempt nor the ephemeral result-read lane owns candidate mutation. No new Task state, Agent role, resource binding, generic workflow engine or arbitrary parent setter is introduced.

Backend owns canonical applicability, operation/outbox admission, immutable candidate/scan/finding histories, authenticated receipts and Owner projections. Runner owns physical source/parent verification, fsynced private intent/ref/results and bounded scans. Web reads canonical metadata and sends exact authenticated commands. Natural-language output changes no formal state.

## Identity and public ancestry

Reuse full original `ResultReadIdentity` and its canonical digest. Store effective Specification/Plan/exact carry evidence separately. Candidate construction identity binds source workspace revision, exact result tree, fixed repository/target, ordered verified public parents and frozen controlled metadata. Rule/policy/permission changes produce a new scan identity and may reuse the identical head; they do not rewrite the original operation or candidate.

First parent is the original remotely verified materialization base. Runner proves it from the successful original open journal operation/outcome, service-private completed pin intent and exact service cache pin, not mere OID existence. Validate repository and storage lineage. An optional distinct target parent requires matching verified fetch/pin evidence and actual ancestry integration in the immutable source. Private Agent/completion commits cannot become parents. A later parent can only be a last reconciled published delivery head; production reconciliation is absent until the next leaf. A prepared/rejected candidate is never treated as published. Unknown remote outcome blocks replacement at the typed seam.

Construct with `commit-tree` using the exact retained result tree, fixed author/committer identity, persisted timestamps and a fixed safe Task/version message. No Agent commit message or free text enters public metadata. Persist input before construction. Set `refs/monos/candidates/<operation_id>` by absent-to-exact CAS inside the trusted result export; keep original result ref, HEAD, private ancestry and workspace unchanged. Verify tree, ordered parents and head before returning. Save immutable manifests; conflicting refs/inputs require reconciliation.

## Durable transport and backend records

Add an additive version-22 migration for Delivery items, stable local operations (the durable outbox), candidates, scans, findings and exact override receipts. An operation holds canonical request/digest, frozen construction and scan configuration, safe status, retry timing and exact source/effective basis. Serialize one unresolved operation per item under DB locks; unique immutable input prevents two workers creating alternatives. Do not put these records in Attempt operations/outbox/inventory or requirement-publication slots.

Automatic admission occurs once REVIEW and physical ownership settlement are canonical. A durable reconciliation pump also admits preexisting eligible REVIEW results after restart. No-change/repository-free results create no item. Both resource modes admit the same local work. Actual requirement/Replan publication pauses incompatible admission; Cancel prevents new dispatch. Late results remain history and cannot restore current evidence. Ordinary pending input remains a later remote guard, not a reason to pretend a local scan failed.

Backend does not know the base tree from the existing result contract and must not infer modification from unequal commit IDs. Admit a Task/resource-owned preparation operation with nullable delivery item first; Runner compares actual immutable base and result trees. A no-change result settles `not_applicable` without creating a Delivery item/candidate. Create the item only for proved modified settlement, retaining operation admission serialization by Task/resource even before an item exists.

Freeze a strict generated `PublicationPrepareRequest`, source/parent descriptors, construction manifest, scan configuration, redacted finding, result/page, ack and optional recovery inventory contracts. Negotiate `publication_modes:["local_candidate_v1"]`. Use separate `publication_prepare`/`publication_result`/`publication_ack` system frames and a bounded two-worker Runner lane. Protocol owner freezes exact field names, canonical digest algorithms and route schemas before dependent writers begin. Full request identity is stable across WSS incarnation changes; each physical reply remains bound to the authorized Runner/socket/incarnation.

Runner persists private intent and sanitized result/pages with 0600 atomic file+directory fsync under a validated 0700 service/publication directory. No SQLite Attempt effect is fabricated. Disconnect/deadline stops work but retains recoverable intent/ref. The same authorized request resumes/replays after reconnect. Backend accepts only exact request/source/tree/parents/construction/scan echoes, persists immutable evidence, then acks. No DB transaction spans provider or Runner I/O. Missing retained storage does not silently clone/fetch/re-export.

Findings require bounded immutable pages: maximum 64 findings and 512 KiB encoded per frame/read, total 4096 findings and 8 MiB sanitized evidence. Choose a dedicated findings read exchange or durable paged result frames during protocol freeze; either binds operation/candidate/scan/page identity and complete counts/digest, and backend cannot mark complete before all pages match. An oversized evidence set is explicitly incomplete, never truncated pass. Web history pages contain at most 32 metadata records and direct selection can resolve older exact candidates.

## Scan algorithm and pinned policy

Enumerate all newly reachable commits using `rev-list head --not <verified public baselines>`. For each commit union changed/introduced versions against every parent, including deleted-path workflow events; inspect the complete final tree as well. A synthetic newly reachable add/delete chain must detect the historical token. Conversely a private Agent add/delete excluded from controlled candidate ancestry must remain private and does not fail a clean exported tree merely because it exists internally.

Evaluate `.gitignore` for each exact tree using Git-backed pattern-only temporary materialization/index; disable global/info excludes, hooks, filters, replacements, lazy fetch and submodule traversal. Verify nested negation and deletion with actual Git. Symlink contents are literal; gitlinks are metadata. Unsupported paths/ignore semantics or missing objects yield incomplete. Stream blob contents in 64 KiB chunks with bounded overlap and full content SHA256 only after complete reading. Binary content is not exempt.

Pin policy version `local_publication_v1`: 50 MiB local per-blob policy; >100 MiB GitHub ordinary-Git provider limit, noneligible. These are separate from processing bounds: 256 new commits, 8192 paths/tree, 32768 version occurrences, 512 MiB aggregate unique blob bytes, 128 MiB/blob, 4096 findings/8 MiB evidence, 4096 UTF-8 path bytes, 120-second processing attempt. Exceeding processing bounds is incomplete and noneligible. Tests may inject smaller validated configurations to exercise boundaries without large resident allocations. Pack-size/provider delivery success is not certified by local blob scanning.

Finite versioned credential rules: PEM private-key headers (PRIVATE KEY, RSA, EC, OPENSSH), classic GitHub token prefixes with bounded token characters, fine-grained `github_pat_` form, and AWS AKIA/ASIA access-key forms. No arbitrary user regex or claim of detecting every credential. Scanner persists only rule ID, commit/path/blob/content digest, size/limit and safe fixed messages. Never persist/echo match bytes, snippets, raw Git/provider stderr or matching-value hashes. Rule matching and overlap lengths must be documented and real tested.

Paths and baseline paths can themselves contain a credential matching the configured rules. Before public finding emission, redact such paths to a fixed placeholder with an explicit redaction flag and opaque deterministic occurrence ordinal. Exact paths remain only in protected Runner source evidence, not backend finding records, UI, public journal or logs; do not emit a plain credential/path hash. Ordinary safe paths retain exact attribution. Finding IDs hash candidate manifest/configuration/scan-run identity plus sanitized finding facts (including occurrence ordinal), preventing cross-version identity reuse without circular dependence on the final scan digest.

Tracked-ignore, local-size and configured credential policy findings are eligible for exact Owner override. Provider hard size, unknown/missing workflow write permission, unverified parents and incomplete coverage are never eligible. Workflow additions/modifications/deletions/mode changes throughout the new range matter; unchanged inherited workflows alone do not require a new finding. Existing read credentials establish no workflow permission. This leaf records the exact relevant configuration/credential fingerprint with permission `unknown` unless an actual verified observation exists. A read-only permission observer and mandatory fresh write authorization belong to the next remote preparation leaf; no inferred grant is allowed here.

If any scanned credential version's blob OID (or verified complete content digest) is already present at any path in an exact verified public baseline, retain a noneligible `published_credential` finding with original baseline commit/path attribution and explicit remediation reason. Renaming/copying the same published blob cannot make the exposure eligible. Do not rescan all excluded old history or infer absence of prior exposure. Known published-sensitive facts persist through the future delivery seam; deleting a newly observed candidate file never rewrites or erases already-published history.

Owner records expose `known_public_exposure_count`, derived from immutable historical published-credential facts scoped to the same Delivery item/fixed repository/Task resource. A later clean/deleted/no-change result or new scan cannot clear that guard. Repeated scan occurrences do not invent additional distinct exposure facts. Keep scan coverage/outcome truthful and display the separate blocking remediation history; no local remediation setter or eligible override can resolve known public exposure. Prefer a scoped query over the existing append-only finding history rather than another mutable authority table.

## Exact commands and applicability

Implement dedicated local retry and finding-override contracts through the existing authenticated Owner receipt/confirmation patterns. Retry only resends/reconciles the original stable operation. A changed rule/config admits a distinct scan authorization. Override confirmation binds Task/effective basis/source/candidate/head/tree/ordered parents/scan/rules/config/permission and the sorted exact finding IDs. Validate all selected IDs and eligibility atomically; mixed hard/eligible, stale, foreign, empty or duplicate selection rejects the entire command. Replay identical request returns the same immutable receipt; conflict rejects. Never set accepted-delivery operation/input cutoff or execute `accept_delivery`.

Distinguish interrupted processing from an already committed incomplete scan. Interrupted processing resumes the same immutable operation. A terminal incomplete scan remains immutable: explicit authenticated Retry admits a new scan-run/operation identity over the same construction/candidate, preserving the prior outcome. Scan identity binds immutable inputs plus its run and coverage outcome. Reuse the original frozen construction metadata/head/ref for rescans rather than freezing new dates. No background loop repeatedly retries terminal incomplete findings.

Read current applicability from canonical result evidence plus relevant current configuration. Preserve historical candidates/scans/receipts after Cancel, source replacement or policy changes. A receipt never erases a finding or authorizes remote writes. Future remote preflight must check all unresolved findings, current complete coverage and fresh provider authority independently.

## Owner view

Strict no-store/nosniff Owner-session reads list candidates and exact scan findings. Add a local candidate section beside each Git result, with distinct result-tree/head/parents/source and effective-basis labels. Show preparing, offline/unsupported, retained evidence unavailable, incomplete, complete with redacted findings, complete without findings, historical and after-acceptance deferred states truthfully. Exact retry/override confirmation controls are available only for applicable eligible records. Session/query keys fence selection/logout/late replies. Use expandable provenance and bounded paginated findings, safe React text, mobile 44px controls and contained overflow. Passing local checks makes no PR, acceptance or secret-free claim.
