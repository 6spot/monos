## Findings

### Architecture and bounded scope

`docs/04-workspace-and-git.md:299` requires exact effective Specification/Plan, current activations/Artifacts, original result tree, candidate head/parents and fixed target. Accept freezes a delivery operation and an input cutoff atomically. `docs/04-workspace-and-git.md:347` defines both message/acceptance orders; `:353` and `:365` require conversation-only later input and exact no-change/non-Git acceptance. `docs/06-state-and-formal-data.md:419` distinguishes batch admission from COMPLETED and requires Cancel to reconcile outstanding effects. `docs/05-tool-protocol.md` requires authenticated receipt-first atomic consumption, not natural-language approval. `docs/08-principles-and-non-goals.md` preserves one Owner, provider-neutral Git identities, revision-specific evidence, physical isolation and independent Tasks after delivery.

Minimum Stage A finalization: zero modified repositories (repository-free or proved no-change), or exactly one modified GitHub repository with automatic preparation and a finalized local candidate/complete admissible scan. Accept can precede the first push/PR and wait for checks. Keep complete collection-shaped output/repository identities. Reject multiple modified repositories, plain-Git finalization and `after_acceptance` with a typed unsupported result before approval consumption or final remote effect. An empty PR list, absent publication record or zero new mapped commits is **not** proof of no change. A mapped result can still require merging its existing published head. Parent clarified this acceptance-before-push requirement during research; it governs this report's proposed integration.

No generic workflow engine, Runtime Attempt for delivery, new Task state, automatic Task creation, forced push, workspace transfer or mutable historical manifests is needed. Worker polling fits the existing server pump.

### Proposed exact protocol boundary

The following names/contracts are proposals for the parent to freeze before implementation, not existing endpoints:

```text
POST /v1/owner/tasks/delivery/commands
GET  /v1/owner/tasks/:task_id/delivery
GET  /v1/owner/tasks/:task_id/delivery/proposals/:proposal_id
GET  /v1/owner/tasks/:task_id/delivery/batches/:operation_id
GET  /v1/owner/tasks/:task_id/delivery/commands/:request_id

OwnerDeliveryCommand = strict discriminated union:
  schema_version:1, request_id:Id, task_id:Id, name, payload
  prepare_delivery_acceptance: {basis:TaskBasis}
  confirm_delivery_acceptance: {proposal_id:Id,content_digest:Digest}
  accept_delivery: {proposal_id:Id,confirmation_id:Id,content_digest:Digest,
                    basis:TaskBasis}
  retry_delivery: {operation_id:Id,expected_version:PositiveCounter}
  cancel_delivery: {operation_id:Id,expected_version:PositiveCounter}
```

Use `additionalProperties:false` and required fields on **each variant**, safe counters, canonical digests and existing bounded text/ID schemas. Do not make one permissive payload containing optional fields for every action. Preparation is Owner-triggered deterministic snapshot assembly; no Agent can invent a delivery proposal. Dedicated confirm validates the current entire proposal, writes the real authorization plus exact Owner command linkage and receipt without changing Task control. Accept consumes that exact authorization and returns committed admission with stable operation/cutoff; it does not claim remote success. Command results distinguish committed receipt from unknown lookup; batch reads expose mutable progress separately. New results may include Task scope explicitly, but SQL must follow actual chosen schemas rather than assuming fields borrowed from another result type.

System-built `DeliveryAcceptanceManifest` should contain:

- Schema version, Task ID, effective Specification and Plan identity/digests, exact reviewed Task basis, and the **complete sorted** output membership.
- Each output: Node/activation/source/Attempt, completion operation and original manifest/digest (including selected Artifacts and handled guidance IDs), plus explicit current applicability/carry evidence. If full Artifact content is not embedded, exact immutable IDs/content digests suffice; never infer current evidence from every published Artifact or latest timestamp.
- Complete sorted repository entries with explicit `no_change` versus `modified` outcome. A modified entry binds stable delivery item/resource, repository identity, original source and digest, original retained source tree/commit/storage, fixed target/delivery ref, preparation operation/request/result digests, exact candidate manifest/head/tree/parents, effective basis, configuration and applicable scan/digest, mapping/digest when present, actual eligible waiver selections/receipts, retained published proof and exact PR identity/ref/base/marker when already prepared. The old candidate's source is not relabeled on mapped carry.
- Repository-free outputs bind their completion manifests and evidence with an empty repository collection. No-change entries bind the terminal `not_applicable/no_change` local preparation request/result. Never require a nonexistent PR or Git identity for repository-free outputs.

Enumerate effective `plan_nodes` and resolve each exact successful completion using `resolveCanonicalResult`; compare complete membership and reject missing/incomplete/over-budget collections. The existing local candidate pump selects one newest Git completion (`publication-candidates.ts:41`) and therefore is not a complete acceptance enumerator. Prefer the existing canonical result/source validators plus owning publication guards over a generic validation engine.

Do not require push/PR existence or required CI success at initial acceptance: remote preparation and checks may remain pending while an accepted REVIEW batch proceeds. Require the finalized exact local candidate, complete applicable scan with explicit workflow fact, actual admissible waiver coverage and settled local work. Freeze existing retained publication/PR identities when present; otherwise freeze repository/ref/marker/target identity and attach the exact eventual push/create receipts under accepted authority. Checks/protection readiness can be evaluated by the accepted worker. Freeze result/target identity, not a timeless assertion about mutable target head or checks. Store provider observations as separate exact head/base scoped facts.

The final input cutoff is the locked Task `conversation_sequence` at **accept admission**, not the proposal preparation time, last processed watermark or first remote dispatch. Acceptance approval binds the result; unrelated preacceptance conversation can be resolved without changing it, while unresolved ordinary input still blocks admission. The successful transaction owns the cutoff even when dispatch never runs.

### Admission transaction and lock ordering

Use the repository's existing hierarchy: Owner session/authentication -> configuration shared lock -> scoped request serialization if used -> discovered Runners in sorted order **only if writing Runner/Attempt/physical records** -> Task control -> proposal/authorization -> stable delivery items in resource-ID order -> owned batch/effect records.

Plain Accept/prepare/confirm only validate settled immutable completions/preparation and write Delivery records; they need no Runner row mutation, so configuration -> Task -> owned records is sufficient. If Cancel stops a live conversation or touches capacity/Attempts, discover/lock affected Runners before Task and revalidate the discovery, as `TaskConversation.command` does at `:90`. Never discover and acquire a new Runner under Task. Keep provider installation reservation lock ordering consistent with the current provider path; never perform provider/Git/credential I/O inside transaction.

1. Authenticate before any replay; check stored request digest before new scope/basis/eligibility checks, then recheck under Task lock where needed. An old committed command still replays after COMPLETED/CANCELLED or stale basis. Changed bytes conflict before target lookup.
2. Lock Task. Require REVIEW, effective Plan and every member completed/current, no active accepted batch, no publication slot, unresolved Replan/planning issue, ordinary input/requirement/guidance guard or physical Node/workspace effect. `taskInputGuards`, `specificationFrozen`, `remoteItemQuiescent`, exact completion/source resolution and ordinary publication/remote guards cover much of this. Check queued nonconversation work and outstanding completion/open/Stop operations explicitly; `localAdmissionAllowed` alone checks process/leases but is not a full effect proof. Unknown/started/may-have-mutated predecessor remote effects conservatively block Accept until reconciled. A compatible pending remote effect can be nominated under the exact rule below.
3. Rebuild/compare the exact reviewed manifest and basis; verify proposal expiry/revocation/currentness, supported resource modes and complete findings/waiver coverage. Retained mapped/publication evidence must match current effective basis and scan. A waiver for an old mapping/scan is insufficient.
4. Consume exact confirmation; insert immutable batch manifest, accepted item memberships and durable pending work; record real acceptance authorization-command/admission receipt linkage. Set Task accepted operation/cutoff to the new batch and append formal acceptance event in that transaction. Batch identity/freeze must not depend on an active browser/Planner.
5. For empty modified-item collection, append completion fact/event and set COMPLETED in this transaction only after exact local/output guards settle. Otherwise remain REVIEW until the supported accepted item finalizes. Retain batch/cutoff history on success; later terminal chat remains conversation-only.

No arbitrary wait for later conversation: at admission, earlier ordinary pending input genuinely blocks. A previously committed reply's repository-free cleanup can conservatively settle first; after admission, later reply processes never become delivery guards.

**Message first:** message obtains same Task row, appends ordinary input with null batch attribution and commits. Accept then sees unresolved guard and rejects without consumption/batch/merge intent.

**Accept first:** batch/cutoff/receipt commits first. Later submission locks Task, stores that batch on input, increments only conversation sequence and queues reply-only source. Checks/merge/failure/Retry/restart follow the frozen batch even if replies are pending/failed/withdrawn or a later reply Stop increments unrelated bookkeeping. No message is lost, relabeled implemented or converted into execution authority.

### Frozen worker authority and completion

Add a dedicated acceptance-scope validator in the owning Delivery module. It verifies actual batch identity and exact immutable manifest/receipt chain, current accepted pointer, not explicitly revoked/cancelled, exact item membership/result/candidate/mapping/configuration/waiver proof and no conflicting effect owner. It checks material changed result/config/provider authority honestly. It must **not** compare original acceptance `control_version` to current Task control, use current conversation sequence as a CAS, call `taskInputGuards` for later input, or require all Planner processes released.

Block new **ordinary** local/remote preparation on accepted Tasks and explicitly allow the accepted preparation lane for that frozen candidate. Without that gate and branch, `ensureLocalCandidate` and `RemotePreparation.admit` may prepare a new source; conversely `ordinaryRemoteAdmission` can pause the approved source on a running later Planner. Automatic push/create/update still use existing Runner/provider request shapes and effect machinery, but each is nominated by the batch and checks accepted authority instead of ordinary input/process guards. Read-only polling/reconciliation continues against the same identity. Make preacceptance preparation Retry/override UI and commands reflect the freeze; accepted Retry owns recovery of nominated operations.

**Exact compatible pending nomination rule:** under Task/item locks, an existing remote operation may transfer dispatch authority to the batch only if it is active, `state='pending'`, `may_have_mutated=false`, `effect_owned=false`, no unresolved claim/effect/worker and not reconciliation-only; its Task/resource/item/Runner/storage/repository/ref/target, preparation request/result digests, candidate head/tree/parents/manifest, effective source/basis/mapping/configuration/scan, actual waiver proofs, workflow fact, expected predecessor head and deterministic provider content all exactly match the frozen accepted manifest. Permit push/create/update only; close/foreign/incompatible operations cannot be nominated. Immutable request bytes and operation ID stay unchanged. Persist an immutable batch-operation authority row binding batch/item/operation/request digest; the Runner body cannot grant or change this authority. Revoke incompatible never-started pending work if its guards allow safe revocation, or reject admission and reconcile; never relabel possible old effects. Accept may atomically create the one exact pending nominated push if none exists. Subsequent PR operations append new authority rows from the same frozen item only after their predecessors settle; existing item ownership remains the serialization boundary.

If remote item identity has not yet been persisted by the ordinary pump, admission/accepted preparation may create it from the already existing local `delivery_items` identity and frozen exact repository/ref/target/marker, using the same deterministic construction at `remote-preparation.ts:55`. Missing PR identity is legitimate until exact create reconciliation settles; it never permits an alternate PR or a second POST after uncertainty. Capture safe deterministic title/body (or their immutable rendered bytes/digest) from accepted formal Task/completion facts for future create/update; later conversation cannot alter provider metadata authority.

**Accepted guard signatures proposed:** `acceptedRemoteAdmission(tx,batchId,item,preparation,prepared,operationId?)` verifies frozen identity and returns frozen actual override proofs; an owning dispatcher `remoteAdmissionForOperation(tx,item,operation)` chooses ordinary versus accepted only from persisted batch attribution. Add accepted-source validation to permission observation and Runner access both before and after token I/O. Preserve configuration fingerprint/App/install/key/exact repository/permissions/workflow fact, owning channel/incarnation/claim, current provider scope, scan/exposure and predecessor effect checks. Ignore only postcutoff input and scratch-only conversation Attempt/process/Stop records; physical Node/workspace or conflicting remote writers still block. No refreshed permission may produce a new source/candidate/scan or widened permission profile. `ensureLocalCandidate` after permission refresh must skip accepted Tasks; fresh observation with the same stable fingerprint can authorize the frozen candidate without editing its immutable old proof.

Concrete accepted integration sites are `remote-preparation.ts:35` (frozen localRequest/content), `:73` (dispatch/nominated operation), `:107` (pending push guard), `:159` and `:192` (provider mutation preflight and final admission); `remote-preparation-access.ts:28`, `:46`, `:78` (permission/source and push access before/after grant); and accepted handling in `remote-preparation-commands.ts:30` instead of ordinary new-effect Retry. A server-owned accepted lookup is sufficient; no Agent credential exposure, new Runtime source or extra daemon follows from this branch.

Freeze protection applies to requirement publish, Replan, guidance effects, shared `reactivateSettledNodes` and Node scheduling/promotion. Existing mutableSpecification/routing checks cover many routes, but add the missing shared primitive and scheduler guards rather than assuming REVIEW alone always protects future callers. Conversation stays independent; reply-only source retries and terminal replies remain allowed.

Provider worker admits one exact merge intent under Task/item/batch locks, commits possible-effect ownership before fixed expected-head mutation, and persists a verified final result immediately. Required checks and mergeability use fresh candidate head/current base observations; changed base needs refresh, changed candidate head never inherits approval. Provider permission/transient failure leaves batch/cutoff intact in REVIEW. Retry reuses original batch and exact accepted item, creates no new acceptance or replacement candidate, and cannot authorize another mutation while outcome is unknown.

`docs/04-workspace-and-git.md:220` permits configured merge/squash/rebase and repository-default first-allowed selection. Preserve all three: bind the selected allowed method to the worker's exact admitted merge request, using configured method or deterministic first allowed default; never silently fall back to another method after rejection. Full method/permission/readiness proof belongs to the provider delegate.

For unknown merge, restart/retry performs exact repository/PR/head/base/marker reconciliation only; absent/unavailable/ambiguous truth remains unresolved. A claim timeout or API error is not evidence of no merge. Finalization records verified merged head/merge commit/evidence against that exact accepted item. COMPLETED requires all supported accepted items finalized, using the original approved manifest even with pending later chat. A verified late merge after Cancel records historical truth but cannot overwrite CANCELLED. Detailed provider readiness/method/permission contract belongs to the parallel provider research.

### Owner control conflicts and deferred correction

- **Cancel:** `node-execution.ts:322` and `task-planning.ts:97` reject accepted Tasks today. Add dedicated delivery Cancel and route the Web's accepted-task action to it (or delegate the canonical command to owning Delivery with identical atomic semantics). Serialize with merge admission/finalization; revoke undispatched work, set CANCELLED, append exact Owner decision/receipt and call existing remote cleanup. Preserve any possible merge for reconciliation; do not close/delete branch as an invented undo. Cancel stays available during unknown outcome. COMPLETED still rejects new cancellation; repeat of an already committed cancel replays.
- **Requirements/Replan/guidance/rework:** reject while frozen; ordinary later messages only explain how further work starts through Todo Discussion. No version substitution, new requirement publication, completed-node reactivation or guidance dispatch to the accepted result.
- **Request Changes:** actual review-feedback routing is not implemented by upstream slices. Do not expose a successful placeholder, silently map it to chat or call requestReplan from text. This Stage A leaf can honestly defer that product control with explicit unsupported status while preserving Cancel. - **Material result/auth drift:** retain accepted identity and visible attention/reconciliation; never merge a replacement head, reinterpret later requests or resurrect ordinary execution automatically. A fresh acceptance after explicit correction belongs to a real future revocation path, not Retry.
