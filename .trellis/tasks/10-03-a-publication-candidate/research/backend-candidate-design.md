## Findings

### 1. Implemented facts and architecture requirements

**Implemented:** original successful results already have a strong source identity. `apps/server/src/task-result-reads.ts:105` joins the original completion manifest, successful physical operation, Node completion, Attempt and workspace. Line 107 derives current applicability from effective Plan membership, completed activation, Task cancellation and exact carry edges. The carry SQL at line 56 binds the original completion operation and manifest digest; activation membership alone is insufficient. `apps/server/src/task-result-reads.ts:201` constructs the complete `ResultReadIdentity`, including original Spec/Plan attribution, physical storage/generation/lease and Git commit/tree. `apps/server/src/task-result-reads.ts:215` resolves a specific original result directly rather than assuming the first history page contains it.

**Implemented:** successful completion records the Node result, releases physical ownership, then derives local REVIEW. See `apps/server/src/service.ts:529`, lines 536–537, `apps/server/src/node-completion.ts:29`, and `apps/server/src/owner-execution.ts:24`. The derivation at `apps/server/src/owner-execution.ts:34` prevents REVIEW while Attempts, workspace operations or leases remain unresolved. `apps/server/src/node-completion.ts:19` refreshes after recovery but preserves requirement-publication and Replan freezes. Completion after Cancel has a separate truthful settlement event and cannot restore current evidence (`apps/server/src/node-completion.ts:37`).

**Implemented:** `operations`, `outbox`, settlement and Runner inventory are Attempt-owned. `packages/db/migrations/0001_boundary_probe.sql:41` requires an Attempt on every operation; line 55 requires an Attempt on every outbox row. `apps/server/src/service.ts:367` inventories only unresolved Attempts and their operations; line 501 settles operation results through an Attempt. An already-released completion Attempt cannot become the owner of new publication work. Publication preparation must not reopen it, create a dummy Runtime execution or borrow its mutation credentials.

**Implemented:** workspace identity and fixed base/target/storage cannot be retargeted by later configuration edits (`packages/db/migrations/0016_serial_workspaces.sql:10`, line 62). `GitRepositoryResource.remote_preparation` already accepts `automatic` and `after_acceptance` (`packages/protocol/schemas/v1/contracts.json:2885`). Both modes can therefore be represented without a new resource model. Existing `GitHub.repositoryAccess` deliberately requests only one repository's `contents:read,metadata:read` and verifies the issued token (`apps/server/src/github.ts:73`). It establishes no workflow write permission. The encrypted App credentials record has App/installation/fingerprint, not a permission snapshot (`apps/server/src/github.ts:11`).

**Implemented seam, not delivery:** paired `tasks.accepted_delivery_operation_id` / `accepted_delivery_input_cutoff` exist with consistency checks (`packages/db/migrations/0019_task_conversation.sql:7`). Task message admission records their attribution (`apps/server/src/task-conversation.ts:48`). `task_command_proposals.action` includes `accept_delivery`, but generic proposal confirmation is not delivery acceptance (`packages/db/migrations/0004_owner_commands.sql:7`; `.trellis/spec/backend/delivery-contracts.md:11`). No canonical delivery item/operation/candidate/scan/finding/override tables exist in the current migrations through version 21 (`packages/db/src/migrate.ts:8`). No production push/PR/merge coordinator exists. `OwnerCommands` is the actual confirmation/receipt module; there is no source class named `OwnerAPI` (`apps/server/src/owner-commands.ts:76`).

**Architecture, required here:** exact result tree, controlled verified public parents, immutable construction metadata, newly reachable publication commits plus introduced/changed versions and final tree, redacted findings and scoped eligible overrides (`docs/04-workspace-and-git.md:200`, `:273`; `docs/05-tool-protocol.md:236`; `docs/06-state-and-formal-data.md:470`). REVIEW is immediately local and remains REVIEW on publication-only problems. No Git Task state, generic workflow engine, Resource binding, fixed product Role, remote source push or permanent disk-loss guarantee may be introduced (`docs/08-principles-and-non-goals.md`). Stage A is one modified repository/GitHub automatic remote preparation; after-acceptance remote delivery is a later V1 slice, while this leaf must still prepare and scan its local candidate (`docs/09-first-executable-slice.md:36`; assigned PRD).

### 2. Proposal: minimum owning records

Use an additive migration, provisionally `0022_publication_candidates.sql`, registered in `packages/db/src/migrate.ts`. Reviewed SQL owns constraints; extend Drizzle mappings only where useful. Keep old completion manifests, operation results, command receipts, schema versions and existing Runner history immutable. Candidate and scan identity must survive a response loss without depending on a browser.

| Record | Minimum persisted contents and constraints |
| --- | --- |
| `delivery_items` | Stable ID; Task/resource/workspace/Runner/repository identity; fixed target; item version; pointer to applicable candidate/scan. Unique `(task_id,resource_id)` and scoped FKs. Later remote lineage has a last reconciled published-head observation; absence is explicit. A locally prepared head is never recorded as published. |
| `delivery_operations` | Stable operation ID; kind `prepare_candidate` or `scan_candidate`; Task/resource/workspace/Runner, optional item until modification is proved, source/effective basis and canonical envelope/digest/schema version; controlled construction metadata; exact parent descriptors; rule/policy/permission configuration snapshot/digest; state, stage, safe bounded failure/wait reason, retry scheduling. This table itself can be the durable outbox with `next_attempt_at,last_sent_at` and guarded claiming, avoiding another queue table for this leaf. One unresolved preparation owner per Task/resource; exact admission identity/replay uniqueness. |
| `publication_candidates` | Immutable candidate ID, preparation operation FK and manifest/digest; original source `ResultReadIdentity` + digest; effective Spec/Plan/evidence applicability digest; `source_workspace_revision`, exact result tree, candidate head, ordered verified parent set, fixed target, construction-version and frozen metadata. Parent descriptors retain verification provenance, repository/ref/object identity and optional target-integration proof. Unique operation/source-construction identity. Do not mutate an old candidate when replacing it. |
| `publication_scans` | Immutable scan ID/identity digest; candidate manifest digest/head/tree/parent set; scanner/rule-set/policy configuration digest; permission observation digest; traversal algorithm version; completion status `complete|incomplete`; safe failure/limit reason; counts; findings digest and encoded size; eligible finding IDs. Rule/config change produces a new scan identity. |
| `publication_findings` | Immutable per-scan finding IDs, ordinal, kind/rule/version, candidate commit/path/blob OID/content digest, scope `publication_commit|final_tree`, measured/limit bytes where relevant, provider permission where relevant, `override_eligible`; safe fixed description, never matching secret values, snippets, raw stderr or token fragments. Scope via scan FK. Deterministic uniqueness covers exact occurrences, not matching values. |
| `publication_override_receipts` (if local override issuance belongs to this leaf) | Exact Task/effective evidence/result/candidate/head/parents/scan/rules/config/finding-ID set; Owner request/authorization identity; timestamp and immutable envelope digest. Reuse existing Owner request receipts for replay. Store invalidation separately or derive it; do not delete/rewrite the receipt. No generic boolean bypass. |

The first five records are sufficient for current/local history and durable preparation. An override receipt table is required before exposing an actual override command; alternatively retain only the policy eligibility contract in this leaf and implement issuance with the remote-delivery leaf. The parent should explicitly choose that scope before implementation. Local override issuance still authorizes no remote write and does not erase findings.

Scopes are product-neutral Git/Delivery facts. `task_publication_slots` owns requirement/Replan publication today and must not be reused as a new generic workflow engine or held throughout a publication scan. Candidate construction reads immutable exports and changes only its own service-private files/refs, so it needs its own item operation ownership, not a Task workspace writer lease.

**Construction versus scan configuration:** separate the construction digest from the scan digest. A rule/size/permission configuration change normally rescans the identical candidate rather than creating a new Git commit. Full relevant policy/provider configuration provenance must be retained, but an unrelated Role edit/global configuration version increment should not unnecessarily change candidate identity. Record the observed global version for audit plus the digest of the actual relevant snapshot. A changed Spec/Plan/evidence basis requires fresh applicability/authorization even if the tree and candidate head remain identical.

### 3. Proposal: deterministic automatic admission and recovery

Factor a server-internal canonical result resolver from `task-result-reads.ts`, keeping the existing authenticated Owner wrapper. Internal workers resolve canonical rows under Task locks, never invent an Owner session, use stale client Git OIDs or call filesystem paths on the backend.

Suggested internal signatures:

```ts
resolveCanonicalResult(tx, { taskId, operationId }): CanonicalResult;
ensureLocalCandidate(tx, { taskId, source, effectiveBasis, configuration }): PreparationReference;
PublicationPreparation.pump(limit = 16): Promise<void>;
PublicationPreparation.pending(runnerId, incarnation): Promise<PublicationPrepareFrame[]>;
PublicationPreparation.finish(runnerId, incarnation, reply): Promise<void>;
taskPublicationCandidates(db, ownerToken, sessionId, taskId, query): Promise<CandidatePage>;
publicationFindings(db, ownerToken, sessionId, taskId, candidateId, scanDigest, cursor?): Promise<FindingPage>;
```

1. Add `ensureLocalCandidate` when completion/state-refresh has reached REVIEW and ownership is settled. Insert operation/intents in the same transaction as publishing current completion/REVIEW whenever possible. Extend recovery paths as well as the normal completion path. A durable pump also enumerates canonical REVIEW Tasks whose exact current Git result lacks a corresponding preparation, covering restart and preexisting results. This is deterministic reconstruction, not another Agent dispatch.
2. Admission lock order follows existing configuration SHARE -> Runner -> Task -> item -> operation, without external I/O. Resolve the exact completed result and original identity, effective Spec/Plan/applicability, fixed resource/target and current parent authority. Stage A rejects a second materialized repository explicitly. Repository-free/no-change results have `not_applicable` read status and create no Git delivery item merely because a workspace was opened (`docs/04-workspace-and-git.md:341`). The existing result response lacks the base tree, so the backend cannot infer no-change from commit inequality. Admit a Task/resource preparation operation with no item pointer; Runner verifies base-tree versus result-tree equality from immutable objects, returning an exact no-change fact or modified candidate. Create the stable delivery item only with proved modifications in guarded settlement. A no-change operation remains infrastructure history rather than a delivery item.
3. Freeze the operation payload before dispatch: source identity, verified parent descriptors, controlled author/committer identities, exact author/committer timestamps, safe deterministic Task/version message, object format, metadata/construction version, relevant scan configuration and bounds. Freeze dates once; retry must not run `now()` into commit identity. Never copy Agent commit messages, private author metadata or workspace paths into public candidate metadata.
4. Construct from retained immutable source export, not mutable Task Workspace HEAD. First parent is the fixed remote-verified base; later parent is the last reconciled published delivery head, not the last locally prepared/rejected candidate. An additional verified target requires explicit proof it was integrated into the result. No arbitrary Browser/Agent OID becomes a parent. Tree equality and each parent's verification/provenance must be checked before accepting the manifest (`docs/04-workspace-and-git.md:279`).
5. **Local preparation runs for both modes.** Pending ordinary input/change can guard later automatic remote preparation without destroying useful local scan availability. Pause admission during actual incompatible requirement/Replan publication; rederive after settlement. `after_acceptance` has an explicit remote-preparation deferred reason, never local-scan `unsupported`. This leaf sends no push/PR/merge instruction and never mints a write token.
6. Backend sends a dedicated typed system `publication_prepare` frame carrying a stable operation ID/digest; Runner returns `publication_result` and an ack follows only after guarded canonical persistence. Add a dedicated pending/inventory/recovery view for these operations, or an explicitly separate generated array in Runner inventory. Existing inventory predicates cannot discover them. Capability negotiation must require this new mode before dispatch; offline/unsupported stays durable waiting and does not create a failed Runtime Attempt.
7. Runner persists a service-private operation intent before creating the commit, then durable candidate manifest/ref and scan evidence. A duplicate exact operation replays that identity and stages. Backend verifies connected instance/incarnation/Runner scope, original envelope digest, exact source/parent/tree/config echoes and bounds; persist candidate/scan/findings atomically before ack. No transaction spans Runner or provider I/O.
8. Serialize claims through database ownership; an in-memory pump flag is only an optimization. If a worker lease is used, expiry grants redelivery of the **same** idempotent local operation, never authority to invent a different candidate. Candidate ref CAS and immutable intent prevent two local writers from producing alternate heads. Redelivery and reconnect must handle commit-created, ref-written, scan-written, reply-lost and ack-lost separately.
9. If source applicability changes during I/O, retain truthful immutable completed candidate/scan as history and decline to install them as current. Cancel revokes new preparation admission and pending dispatch; reconcile already-started local effects to safe retained history. Neither a late result nor a stale candidate can restore REVIEW or current evidence. Preserve accepted-operation/input-cutoff semantics for future remote operations; unrelated chat must not revoke a future frozen accepted batch.
10. Physical result/candidate storage remains Runner-scoped. Missing original evidence returns safe recovery attention; never clone/fetch/re-export a substitute implicitly. Retention must account for these unfinished operations and candidate source references. No permanent local disk-loss recovery or cross-Runner transfer is added.

For the fixed-base verification seam, the Runner researcher found existing successful original open SQLite operation/result, its service-private completed workspace intent and exact cache base pin as useful evidence. Merely finding an OID in a retained export proves object presence, not remote verification. Backend stores the verified parent descriptor/provenance digest; Runner must validate the underlying original evidence. Full detail belongs in the independently owned Runner research.

### 4. Proposal: scan identity, range, policies and bounds

Define scan input identity as canonical SHA256 of `{algorithm_version,candidate_manifest_digest,head,tree,ordered_parents,verified_baseline_oids,rule_set_digest,policy_config_digest,permission_observation_digest,bounds}`. Freeze a separate `scan_run_id` in each admitted scan operation; its immutable persisted outcome/digest identifies the exact findings and completeness snapshot. Findings IDs derive from the scan identity plus exact rule/commit/path/blob/scope occurrence; never hash and expose the credential match itself. A successful response with changed identity is a payload conflict, not a fresh scan result for the old operation. Redelivery before outcome commit resumes that same run. If an incomplete outcome has already committed, an explicit Retry creates a fresh scan-run operation against the same candidate/input configuration (or a new configuration after repair) and preserves the earlier outcome; it does not mutate an immutable incomplete row into complete. Override/API `scan_digest` binds the exact completed run outcome as well as input identity. Do not make input digest uniqueness prevent a legitimate explicit fresh run.

Traversal must inspect `reachable(head) - union(reachable(recorded verified baseline parents))`; it must not scan only a fixed-base-to-final net diff. For each newly reachable commit inspect introduced/changed blob versions across **every** parent using non-combined diffs/union, including versions absent from the final tree; inspect final-tree tracked files too. Enumerate commit/tree/blob facts deterministically and stream bounded content checks. Cache content analysis per blob/rule, but preserve path/commit occurrences because ignore/workflow meaning is path and version dependent. Ignore policy uses candidate-version tracked files and ignore files, not service `$HOME`/mutable local excludes. Symlinks are literal blob contents and gitlinks are metadata, with no target traversal or submodule fetch. Missing object, unsupported path, missing required rule, scan byte/object/time/findings limit or unknown relevant permission produces **incomplete**, never a passing partial scan.

**Important test distinction:** normal exact-tree export with all direct parents already verified remote generally has one new synthesized commit. A private Agent commit adding then deleting a token must remain outside its ancestry and must not incorrectly fail publication just because private history retains that token. Separately, test the range scanner against a synthetic candidate/publication range with an introduced token and later deletion: that blob must be detected even when the final tree is clean. Reject attempts to create such an intermediate private-parent chain through the normal constructor. If content was already published, previously recorded publication findings/exposure facts require explicit remediation; a later deletion is never represented as erasing published history (`docs/04-workspace-and-git.md:295`).

| Finding | Evidence / override contract |
| --- | --- |
| `tracked_ignore` | Commit/path/blob plus exact ignore-rule/configuration identity. Policy eligible only if that rule explicitly permits Owner override. Ignored untracked files are not added to completion. |
| `publication_policy_size` | Actual blob bytes and separately configured policy limit. Proposed default warning/blocking policy: 50 MiB; eligible only by policy setting. This is not a local capture limit. |
| `provider_hard_size` | Actual ordinary Git blob bytes > 100 MiB, provider/rule version. Never eligible. Cannot disappear by deleting that blob in a later newly reachable commit. |
| `credential_pattern` | Exact blob content digest, commit/path/rule and safe fixed label such as “Credential pattern matched; value redacted.” No matched text, context, prefix/suffix or matching-value hash in UI/receipts/journal/errors. Eligibility explicit per versioned rule; scans do not prove absence of all secrets. |
| `workflow_permission` | Candidate-range changes under literal `.github/workflows/` plus required `workflows:write` and current installation observation. Missing/unknown permission blocks readiness and is never eligible. Deletions and changes later undone still need range-aware evaluation. |
| `scan_incomplete` / `parent_unverified` / `provider_authorization_unknown` | Infrastructure/authority attention rather than waivable content policy. No override can make incomplete evidence complete or manufacture provider permission. |

Initial credential rules need an explicit reviewed versioned set of synthetic provider-token/private-key detectors, not an unversioned ad hoc regex or a promise to recognize all secrets. Avoid arbitrary Owner regex execution. Rule definitions and eligibility live in a source-owned policy module; immutable operation configuration records their digest.

Use separate scan processing bounds and response bounds. Proposed initial Owner page: up to 64 findings and <=256 KiB encoded JSON; whole Runner frame <=1 MiB including wrapper; operation/result reserve >=4096 bytes as existing protocol requires. Findings path limits use existing 4096-byte literal path/Unicode contract. Runner research proposes 256 range commits, 8192 paths per tree, 32768 versions/findings, 512 MiB unique analyzed blob bytes, 128 MiB streaming per blob, 120-second deadline and a separate two-worker lane. These are proposal values requiring one design authority, not existing limits. The sibling proposes 16 MiB configured publication policy while this file illustrates 50 MiB; parent must pin one configurable monos policy independently from the 100 MiB provider hard limit. Findings overflow must surface incomplete status and bounded redacted observed evidence/counts, never silently truncate into `complete`. Do not reuse 64 KiB result-inspection text limits as scan limits: that would disable credential analysis on valid larger publication blobs. If using a single result frame, explicitly bound total findings to fit; otherwise define immutable page digest/ordinal assembly and commit a complete scan only after every validated page is received. Read pages are not separate successful scans.

**Primary external facts, checked 2026-10-03:** GitHub warns on ordinary files larger than 50 MiB and blocks files larger than 100 MiB; browser upload limits differ, and Git LFS is a different delivery mechanism. [GitHub large-file limits](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github). The newer repository-limits page says push limit 2GB and describes enforced single-object size as “100 MB”; it does not state that a scan of uncompressed blobs proves an exact negotiated pack size. [GitHub repository limits](https://docs.github.com/en/repositories/creating-and-managing-repositories/repository-limits). Pin ordinary-file bytes as 100*1024*1024 using the specialized page; record the conflicting unit wording as a caveat for real-host provider boundary validation. The 50 MiB configured policy is a proposed monos policy, not a GitHub hard rejection. Do not label the repository-wide recommendations or inspection limits as provider hard limits. This local leaf cannot certify future total push-pack success; enforce a separate bounded pack-budget policy/preflight in the remote leaf and never make the 2GB provider ceiling overridable.

GitHub's Git-access documentation requires Contents for Git access and Workflows for editing Actions files under `.github/workflows`. [GitHub App permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app). Reference creation/update docs expose Contents-write and Contents+Workflows-write permission sets; these REST sets alone are not proof of a tested live Git push. [GitHub ref permissions](https://docs.github.com/en/rest/git/refs?apiVersion=2022-11-28). Installation permissions are returned by read APIs, and minted tokens cannot exceed granted App permissions. [GitHub App installation API](https://docs.github.com/en/rest/apps/apps?apiVersion=2022-11-28). Keep existing pinned `2022-11-28` request behavior until an explicitly tested API version migration; current docs examples have changed and do not automatically migrate production code.

For permission evidence, add a **read-only** bounded backend App-installation permission observation (e.g. JWT-authenticated GET of the exact installation, with repository identity verification) or report `unknown` while content scanning succeeds. Never infer permission from a resource field, encrypted-key existence, successful anonymous read or deliberately narrowed read token. Keep observation repository/App/installation/fingerprint and relevant configuration bound; retain no token/JWT/private key. Recheck live permission immediately before a future remote write. An unknown observation can show a workflow change finding today; it cannot become an overridable “warning.”

### 5. Proposal: Owner API, UI and override enforcement

Suggested strict generated reads:

```text
GET /v1/owner/tasks/:task_id/publication-candidates?source_operation_id=...&cursor=...
GET /v1/owner/tasks/:task_id/publication-candidates/:candidate_id
GET /v1/owner/tasks/:task_id/publication-candidates/:candidate_id/findings?scan_digest=...&cursor=...
```

Use exact Task/candidate/scan-bound canonical cursors; up to 32 candidate records per bounded history page, findings separately paged by bytes/count. Authenticate the Owner cookie and `X-Monos-Session` before each read, then resolve fresh applicability from canonical results and candidate relevant configuration. Responses carry `no-store,nosniff`. Server returns original source identity and effective basis separately, preparation state/recovery reason, `current`, `scan_applicable`, scan completeness and safe readiness/guard reasons. Browser never supplies candidate head, arbitrary path/OID or its own claim that the scan is current. Old candidate/scan reads remain available after replacement and Cancel without becoming current; check direct selection past page one.

If Retry/overrides are in scope, a dedicated local `PublicationCommand` family can use existing Owner command receipt/storage patterns:

```text
retry_publication_preparation {task_id,request_id,operation_id,operation_digest}
override_publication_findings {task_id,request_id,candidate_id,candidate_manifest_digest,
  effective_basis_digest,scan_digest,finding_ids,confirmation_id}
GET /v1/owner/tasks/:task_id/publication/commands/:request_id
```

Retry reconciles and resends the original operation; fresh configuration/rules admit a new scan operation. A new envelope is not an automatic retry of an unknown request. For overrides use an exact displayed proposal digest and existing Owner-authenticated confirm/consume pattern, with a dedicated action or scoped module. Existing generic `prepareTaskProposal/current` compares whole control basis (`apps/server/src/owner-commands.ts:53`), so future accepted batch workers cannot use that method as their ongoing authority: authority is the frozen batch, exact item/result and explicit revocation. Local candidate preparation does not set either accepted-delivery field and never calls `accept_delivery`.

Override admission locks Task/item/scan and validates fresh current source/effective basis, exact candidate manifest/head/tree/parents, complete applicable scan, matching rule/configuration/permission digest, unique finding IDs all belonging to that exact scan, explicit eligibility for every selected finding, and original authorization. Unknown/cross-scan/stale IDs, empty/malformed selection and mixed eligible+hard findings reject the entire command. Backend derives eligibility; client `eligible:true`, forged `kind`, replaced limit or generic confirmation cannot grant it. A rule update, new parent/candidate or changed result/effective requirement invalidates applicability of all older receipts. Future remote preflight must independently require no unwaived eligible findings, no hard findings, a complete current scan and live provider authorization; it must never treat “has any override receipt” as readiness.

Add `PublicationCandidate` section adjacent to each exact Git `TaskResults` record in `apps/web/src/features/task-overview.tsx:209`, preferably a dedicated `publication-candidate.tsx` composition. Preserve `ResultInspector` and current result inspection. Poll canonical candidate metadata with Task/source/session query keys, fence late responses across logout/selection/scan changes and keep candidate/scan history continuations visible (`apps/web/src/lib/task-api.ts:32`; `.trellis/spec/frontend/execution-ui.md`). Candidate head and exact matching result tree are distinct labels. Public parent identities belong in expandable details; source/evidence attribution remains inspectable.

| Observable local UI state | Required presentation |
| --- | --- |
| No Git / no modification | Clear applicability reason; existing repository-free result remains readable. |
| Waiting / preparing / scanning | Factual progress without percent/ETA; local result inspection remains available. |
| Runner offline / unsupported / retained evidence unavailable | Specific safe reason, original operation reference and Retry when useful; no fabricated empty/passed findings. |
| Complete with findings | Redacted rule/commit/path/object/version/size/limit; current scan identity; eligible policy marker, hard constraints with correction/configuration reason. |
| Incomplete scan | Explicit incomplete/blocking status plus bound/recovery reason; no “checks passed.” |
| Complete with no findings | “Local publication checks complete” for the exact head/version; no acceptance/PR/publication claim or secret-free assertion. |
| `after_acceptance` | Same local candidate/findings; remote preparation deferred until future supported acceptance flow. No functional Accept/publish promise in this leaf. |
| Historical/stale/cancelled | Original mapping/findings retained and labelled; current actions unavailable with reason. |

The existing notice at `apps/web/src/features/task-overview.tsx:225` says REVIEW records no PR/delivery/acceptance; preserve its truthful meaning with candidate-ready wording. No Owner “Prepare PR” step is added. Desktop 1440x1000/mobile 390x844 must show long commit/path wrapping, contained findings overflow, visible statuses and reachable 44px controls, consistent neutral surfaces (`.trellis/spec/frontend/visual-design.md`; `docs/07-owner-review-and-ui.md:670`). Raw match values must not appear in rendered content, serialized read bodies, UI storage, console/server logs, operation status or error paths.

### 6. Proposed files and acceptance checks

Backend additions: `apps/server/src/publication-candidates.ts` (admission/system worker), `publication-candidate-reads.ts` (scoped canonical metadata/findings), `publication-policy.ts` (versioned policy/rules), optional `publication-commands.ts` (local Retry/exact override). Integrate `node-completion.ts`, `main.ts`, `app.ts`, `service.ts` WSS/inventory seams and canonical internal resolver in `task-result-reads.ts`; extend source-aware Cancel and requirement/Replan quiescence checks only for incompatible pending publication work. Add migration/schema mappings. Runner-specific files/limits are assigned separately.

Wire additions belong solely in `packages/protocol/schemas/v1/contracts.json`: strict candidate/source/parent/scan/finding/read/command/system-frame contracts, Ready capability and dedicated recovery inventory. Generate TS/Go/embedded schema/OpenAPI via `pnpm protocol:generate`; never hand-edit generated files. Require wrapper/Unicode byte validation and shared TS/Go fixtures for omitted/null/unknown fields, counters, hard-limit/noneligible findings, scan identity and malformed replies. Compile all Go consumers after generation (`.trellis/spec/protocol/schema-generation.md`). Web addition: dedicated candidate component plus `task-overview.tsx`, generated API integration, and `TaskIntent`/journal allowlist only if local commands are actually exposed.

Acceptance tests to write with implementation, not run as evidence for this research:

1. Real PostgreSQL two independent workers/Runner rows contend for one item/source; observe actual DB blocking and one canonical admission. Kill before/after commit; reconstruct REVIEW prep and retain original operation/candidate identity. Registering the new migration must support clean install and version-21 upgrade without changing historical receipts/manifests.
2. Genuine admitted original completion (including finalized settlement recovery) automatically prepares once; repository-free/no-change creates no delivery item. Historical results beyond first 32 entries do not become eligible. Exact carry remains current; refresh/rework/Spec change/Plan replacement/Cancel during I/O preserves old history and removes current scan/override applicability.
3. Reject private/unverified/foreign-repository parents, changed order/parent/head/source/tree/metadata/config payload, candidate tree mismatch and result-only OID authority. Fixed base/target cannot change through Project defaults. Corrected unpushed result uses verified published/base parent and preserves rejected candidate history.
4. Native Git/SQLite/source-export candidate replay across each durable stage and reply/ack loss, controlled public metadata, no internal ancestors/refs in intended publication, same-tree/different-head distinct head checks. Range fixture catches add-secret/delete-secret and oversized historical blob, while private add/delete before exact-tree export remains private. Workflow and ignore rules use actual candidate versions, including intermediate changes.
5. Separate local capture failure from successful completion with publication size/content findings. Boundary bytes at/below/above policy/hard limits; binary/symlink/gitlink/long-Unicode paths; chunk boundaries, all-parent merge diff coverage, complete final-tree scan, every processing/response bound. Limit exhaustion always incomplete.
6. Exact eligible override replay and rollback of authorization consumption; forged/cross-Task/cross-scan/stale/mixed-hard/permission finding IDs reject atomically. Rule/config/permission/result/parent changes invalidate old receipts. Hard size, missing permission and incomplete scans cannot be waived. Candidate/scans/receipt issuance never writes accepted-delivery fields.
7. Both resource modes prepare local candidate/scans identically.
