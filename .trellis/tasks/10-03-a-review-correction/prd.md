# Review correction and delivery recovery

## Goal and user value

Owner can explicitly request improvements to the current integrated result, including
an eligible accepted but entirely undelivered version. The system stops that
version's new delivery effects, settles original effects, and asks Planner to route
the same Task's correction. Explicit exits preserve feedback and remote truth.

## Background and order

Upstream [exact Owner delivery](../archive/2026-10/10-03-a-owner-delivery/prd.md)
was accepted at `c0212a9`, archived at `80f57b5` and recorded at `ea1a15d` on
2026-10-05. It supplies genuine authority, frozen batch/cutoff, automatic accepted
preparation, expected-head finality and original-effect Retry/Cancel. It intentionally
has no Request Changes/revocation/restoration source. Existing Replan supports
Node/input origins and independent exits; it does not yet carry actual review origin.

User standing delegation covers successive planning, implementation, routine design,
scoped commits and marked synthetic verification without approval questions. It does
not supply product Owner acceptance for real work. This leaf precedes combined
installed delivery acceptance; zero configured live GitHub Apps remains that gate.

## Requirements

1. Dedicated authenticated Owner Request Changes binds the current canonical local
   review basis/result digest and readable feedback. Its capability is independent
   of delivery permission/scan/readiness, so those Accept blockers cannot prevent
   correction. For an accepted Task additionally bind exact current batch ID, digest
   and capability version. Replays recover the same recorded action before freshness
   checks; stale/cross-Task actions create no feedback or revocation.
2. Serialize admission with Task control, shared item dispatch and finality. Revoke
   only while no item finalized and no merge outcome remains unresolved. Retain
   immutable approval/batch/input history and add actual Owner receipt-backed
   revocation; cancel pending dispatch. Old accepted operations never regain ordinary
   authority when the Task pointer clears. Settle all admitted original pushes/PR
   mutations, physical writers and relevant scratch Planner work before correction.
   A preparation push is not finality. Request Changes preserves the delivery PR and
   branch; it is distinct from Task Cancel.
3. While routing is queued, running, failed or awaiting an answer, Task stays REVIEW
   and Accept/merge/new ordinary preparation remain disabled. Planner uses a genuine
   read-only/repository-free review source with the effective Spec/Plan, formal result,
   feedback and conversation. Use Rework directly when the graph suffices. Request
   formal Replan only for genuine insufficiency; changed scope uses existing exact
   requirement proposals/Owner confirmation. Clarification creates an actual issue.
   No natural-language reply makes a formal decision.
4. Preserve the same Task/Node/workspace and normally branch/PR. Rework invalidates
   current evidence while retaining code/history and returns through fresh review.
   Every new result requires fresh exact acceptance; neither Withdrawal nor a reused
   result can revive the revoked approval or original mutation operation IDs.
5. Answer & Retry targets the exact feedback/current generation and retains its
   answer for the next source. Withdraw feedback is an independent recorded Owner
   decision, available during routing, which fences the source and waits for actual
   settlement. Dismiss Replan preserves originating feedback, returns to REVIEW with
   a fresh same-feedback routing successor and prevents same-basis automatic Replan
   repetition; it is not Withdrawal. Existing requirement/Replan guards and independent
   controls remain actionable. Failures cannot silently remove feedback guards.
6. After revoked delivery and old reply-only work settle, reconsider later messages
   with ordinary applicability while preserving their original accepted attribution
   and every message/reply/resolution. Pending/failed input uses fresh authority;
   already-replied input creates a new semantic routing obligation, not a duplicate
   reply. Reconsiderations guard acceptance until resolved. Chat alone cannot revoke
   acceptance or request correction.
7. Cancel remains an explicit terminal action under existing physical and shared-item
   guards. Observe/reconcile unknown effects before closing undelivered open PRs; keep
   branches and historical final commits. Task CANCELLED never implies effects stopped
   and late finality never revives it. Any finalized item forbids reopening shipped
   results. Stage A remains zero/one modified automatic GitHub repository; generic
   any-finality guards do not implement multi-repository delivery.
8. Protected Web shows Request Changes, exact feedback/routing/settlement state and
   the appropriate Answer & Retry, Withdraw feedback, Dismiss and Cancel actions.
   Reuse the Task command journal and session/selection fences; no optimistic formal
   state. Expose actual reconciliation/cleanup separately from terminal cancellation.
   Owner is never asked to understand/select the internal graph.

## Acceptance criteria

- [x] **AC1 — Owner and revocation authority:** genuine commands create one feedback
  and, when eligible, one receipt-backed revocation. SQL rejects pointer clearing or
  provenance substitution without the exact recorded authority. Unknown merge,
  stale basis/batch or finalized item rejects without partial state changes.
- [x] **AC2 — effect and routing order:** real PG shared-lock races cover both correction
  and finality admission winners. Held-token/pre-effect worker cannot mutate after
  revocation; actual admitted original preparation settles before routing/Rework.
  Stale linked operation cannot regain ordinary authority after Withdrawal/reacceptance.
- [x] **AC3 — semantic correction:** actual source-bound Planner commands demonstrate
  REVIEW while routing, sufficient Rework with retained Task/Node/PR lineage,
  genuine-insufficient Replan and exact changed-requirement proposal boundaries.
  Fresh accepted result cannot inherit old approval. Stage A finalized result rejects
  correction; no unsupported multi-repository success is claimed.
- [x] **AC4 — explicit exits:** actual issue + answer/retry, routing failure + Retry,
  running withdrawal and review-origin Replan dismissal preserve exact obligation,
  successor and process-settlement guards. Dismissal never silently withdraws feedback;
  same-feedback/same-basis automatic Replan repetition fails.
- [x] **AC5 — later input and Cancel truth:** late pending/failed/replied messages retain
  attribution and original replies, with fresh ordinary routing and no duplicate reply.
  Original effect recovery remains truthful through Cancel; terminal Task never revives,
  and undelivered PR cleanup respects unknown merge and retains branch history.
- [x] **AC6 — wire and Web:** strict generated Owner/Agent/launch/read contracts,
  authentication/Origin/no-store and exact journal recovery pass affected consumers.
  Current built Web demonstrates Request Changes, queued/failed/issue exits,
  accepted revocation settlement, review-origin Dismiss/Withdraw and cancellation
  reconciliation with representative inspected desktop/mobile layouts.

## Design and evidence

Source research is recorded in `research/`: backend routing/persistence, Web/wire
and main delivery effect boundaries. Complex design, ordered execution and curated
implementation/check contexts must converge before product implementation.

## Out of scope

No new Task state, generic workflow engine, artificial input/Node origin, fixed
Agent Outcome taxonomy, multi-repository delivery, plain-Git/deferred mode expansion,
new installed App claim, repeated live merge, product-source push, remote history
rewrite, automatic requirement acceptance, workspace transfer or disk-loss recovery.
Combined installed acceptance remains the next leaf.
